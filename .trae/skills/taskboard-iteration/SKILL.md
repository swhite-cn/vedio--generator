# 任务板驱动迭代（Task-Board Driven Iteration）

把「一次性大需求」拆成可逐个执行、可中断恢复、可审计的编号任务。核心是**三层真相分离**：设计与取舍、当前工作状态、执行证据各归一处，互不覆盖。

本 skill 为通用流程；本仓库的落地实例见 `docs/v2_refactoring/`（§11 参考实例）。

## 0. 何时用 / 何时不用

**用**：
- 需求需要多步、跨多个会话完成；
- 中途可能被打断，必须能凭文档恢复而不是凭记忆；
- 需要留下可审计的执行证据（做过什么、验证结果、遗留什么）；
- 存在依赖关系、需要分批出口判定。

**不用**：
- 单文件小改、格式化、改一行文案；
- 纯问答、纯调研、一次性命令；
- 已有明确任务系统的外部需求（用外部系统，不要双写）。

## 1. 三层真相模型（不可混写）

| 层 | 承载 | 位置（本仓库约定） | 只写什么 |
| --- | --- | --- | --- |
| 设计真相 | 需求、方案、取舍、冻结决策 | `docs/<迭代名>/<方案名>.md` | 为什么这么做、边界、未做项 |
| 工作状态 | 当前进度、依赖、验收标准、日志路径 | `docs/<迭代名>/tasks.md` | **只写状态与判据**，不写过程性叙述 |
| 交付证据 | 每个任务的执行证据 | `docs/<迭代名>/logs/` | 做了什么、验证命令与结果、断点 |

硬规则：
- **同一事实只写一层**。状态在 `tasks.md`，过程在日志，方案在方案文档，禁止三处复制。
- **冲突时以代码/实测为准**，其次方案文档，最后任务板与日志。
- `tasks.md` 是本迭代**唯一的工作状态真相**；日志目录不承担状态 ownership。

## 2. 目录与文件布局

```
docs/<迭代名>/
├── <方案名>.md              # 设计真相（可选，但有多任务时强烈建议）
├── tasks.md                 # 工作状态真相
├── logs/
│   ├── README.md            # 日志协议（命名 / 模板 / 检查点 / 状态耦合 / 跳过策略）
│   ├── T001-<slug>.md
│   ├── T002-<slug>.md
│   └── artifacts/T001/      # 大块证据（命令输出、日志片段），不贴进 markdown
├── screenshots/             # 可选：目检截图（如 t313-<page>-1440x900.png）
└── baselines/               # 可选：性能/回归基线 JSON
```

新迭代**新建独立目录**，不复用旧迭代目录（例如不要在 `docs/v2_refactoring/` 里开新批次）。

## 3. 任务编号与拆分

- 编号形如 `T<批次><序号>`：`T0xx` 基础设施、`T1xx` 第一批、`T2xx`… 依次递进；编号只增不改。
- 同一里程碑内再拆分用字母后缀：`T004a` / `T004b` / `T004`（先做影子改动，依赖就绪后再切换）。
- 同批次新增任务继续递增（`T505`），**不插入不重排**，保持历史 ID 稳定。
- 粒度：**一个任务 = 一个可独立验证的变更集，默认 ≤ 10 个文件**。超过就拆，并在日志「已知风险」里说明为何还要拆。
- 每个任务必须写清「交付 / 验收」——可执行、可判定，避免「优化 XX」这类不可验收的描述。
- 依赖必须无环；有环就说明拆分错了。

## 4. 任务板模板（`tasks.md`）

```markdown
# <迭代名> 任务板

> 设计真相：[<方案名>.md](...)
> 工作状态真相：本文件
> 交付日志：`logs/`（模板见 logs/README.md）
>
> 本文件只记录当前状态、依赖、验收标准、日志路径，不写过程性内容。

## 一、执行协议（每个任务必须遵守）
### 1.1 任务开始前
1. 状态改 `in_progress`，写 `started_at`；
2. 读依赖任务日志，确认前置产出存在；
3. 读方案对应章节，确认不改变已冻结决策；
4. 方案与代码冲突 → 先停下，写 `blocked`，记入「待裁决」，不擅自扩大范围。
### 1.2 任务执行中
- 一个任务只做一个可独立验证的变更集，默认 ≤ 10 个文件；
- 每完成一个可验证步骤，追加带时间戳的 `Checkpoint`；
- 要跑长命令前，先写「即将执行」日志。
### 1.3 任务结束
1. 运行验收命令；2. 写完整日志；3. 改状态；4. 在日志写明下一个任务 ID。
### 1.4 中断恢复规则
- 跨过会话就必须在中断前写 `partial` 日志（已完成/未完成/最后命令/下一步/风险）；
- 恢复先读日志，不凭记忆；**不删除不覆盖旧日志**，在末尾追加 `## 续跑记录`；
- 同一阻塞连续 3 次 → 改 `blocked` 并登记。
### 1.5 不提交约束
- 不要求每任务一次 commit；**只有用户明确要求才提交**；
- 若提交，状态更新与代码改动同一逻辑提交。
### 1.6 状态图例
| 状态 | 含义 |
|---|---|
| `todo` | 未开始 |
| `ready` | 依赖已满足，可开始 |
| `in_progress` | 正在执行 |
| `partial` | 已开始未完成，必须能从日志恢复 |
| `blocked` | 被决策/外部条件阻塞 |
| `done` | 验收命令通过，日志完整 |
| `canceled` | 明确不做 |

## 二、当前焦点
| 项 | 值 |
|---|---|
| 当前批次 | <Mx> |
| 当前任务 | `Txxx`（状态） |
| 上一任务 | `Txxx` |
| 当前阻塞 | 无 / <原因> |
| 下一步 | <下一个任务或明确例外> |

## 三、<批次名>（每批次一张表）
| ID | 任务 | 交付 / 验收 | 依赖 | 状态 | 日志 |
|---|---|---|---|---|---|
| T101 | <任务名> | <可判定验收> | — | done | [T101](logs/T101-<slug>.md) |

## 九、依赖主链
```
T001 → T002 → T003
          └→ T101 → T102
```

## 十、批次出口判据
| 批次 | 出口判据 |
|---|---|
| M1 | <该批次全绿的可判定条件> |

## 十一、变更记录
| 日期 | 变更 | 影响 |
|---|---|---|
| YYYY-MM-DD | <完成/拆分/放宽/裁决> | <对后续任务的影响> |

## 十二、待裁决与遗留项
| ID | 事项 | 来源 / 证据 | 裁决 / 结果 |

```

## 5. 状态机与执行协议

- 状态迁移只允许：`todo → ready → in_progress → done|partial|blocked|canceled`；`partial` 可回 `in_progress`。
- `todo → ready` 的条件是**所有依赖 `done`**；每次审计时校正遗漏的 `ready`。
- **先改状态还是先写日志**：完成 → 先改 `tasks.md` 为 `done` 再写日志；中断 → 先写 `partial` 日志再改状态；阻塞 → 日志写清原因与需要谁裁决，再改 `blocked`。
- 状态变化必须同步「二、当前焦点」表，避免任务表与日志漂移。
- 代码改动与状态更新处于同一逻辑变更集。

## 6. 交付日志模板（`logs/`）

命名 `T<编号>-<短横线英文描述>.md`；同名任务续跑**不新建文件**，末尾追加 `## 续跑记录`。

```markdown
# T0xx 任务日志：<任务名>

## 元信息
- 任务 ID：T0xx
- 状态：done | partial | blocked
- 开始时间：YYYY-MM-DD HH:mm
- 结束时间：YYYY-MM-DD HH:mm
- 关联设计：方案 §x.x
- 依赖任务：Txxx
- 后续任务：Txxx
- 变更文件：
  - path/to/file

## 意图
一句话说明为什么做，以及它解锁了什么。

## 改动
- 做了什么（按文件或模块）
- 明确没有做什么（避免范围蔓延）

## 验证
| 命令 | 结果 | 证据 |
|---|---|---|
| `<可复现命令>` | pass | <数值证据，如 12 passed> |

## 断点 / 未完成
- 未完成项：
- 最后运行的命令：
- 恢复时第一步：
- 已知风险：

## 风险与后续
- 风险：
- 下一步任务：
```

硬规则：
- 「验证」列必须写**真实执行过的命令与结果**，不写「应该没问题」；不可验证项如实登记为已知边界。
- 「明确没有做什么」用于防止范围蔓延，不是可选项。
- 不记录密钥、令牌、真实用户凭据、完整私有对话。

## 7. 检查点与中断恢复

长任务执行中，每完成一个可验证步骤追加：

```markdown
### Checkpoint HH:mm
- 已完成：
- 验证：
- 下一步：
```

- 中断前**最后一次检查点必须含可直接复制执行的恢复命令**。
- 恢复时先读该任务日志与 `tasks.md`「当前焦点」，再继续。
- 恢复执行在日志末尾追加 `## 续跑记录`，不改写历史段落。

## 8. 变更记录 / 待裁决 / 批次出口

- **变更记录（§十一）**：任务拆分、契约放宽、口径裁决、方案偏差等都要留一行（日期 / 变更 / 影响）；它是后续任务理解「为什么现状是这样」的唯一索引。
- **待裁决与遗留项（§十二）**：协议要求「发现方案与代码冲突先停下并记入待裁决」。任何跨任务遗留都必须在这里登记（含证据链接），即使不阻塞当前出口；裁决后回填结论。**没有这一区块时，遗留项会直接漏掉**。
- **批次出口判据（§十）**：每个批次的完成条件是**客观可判定**的（测试全绿、清单逐项核对、指标达标）。出口达成后在变更记录里显式声明。
- **方案偏差**：实现与方案不一致时，二选一——改代码对齐方案，或在**方案侧**登记偏差（写清由什么实现覆盖、为何不加别名）。不要把偏差只留在任务板。

## 9. 与项目约束的衔接（本仓库）

- **语言**：任务板、日志、变更记录、提交信息一律中文；函数级注释中文。
- **不擅自 commit**：除非用户明确要求；不要覆盖或清理工作区已有改动。
- **行为变更必须先补测试**，再跑本仓库验收命令：`pnpm test`、`pnpm run typecheck`、`pnpm build`；涉及渲染/端到端用 `pnpm test:smoke`，性能基线用 `pnpm test:bench`。
- **验收命令要可复现**：写进日志「验证」表时带上完整命令与关键数值（文件数/用例数/耗时）。
- **用户可见行为变化**同步维护 `docs/guides/developer-guide.md` 或 `operator-guide.md`。
- **纯文档/格式化/无行为注释**可不写独立日志，但要在相关任务日志里注明「已随 Txxx 完成」。

## 10. 反模式

| 反模式 | 后果 | 正确做法 |
| --- | --- | --- |
| 在 `tasks.md` 里写过程叙述 | 状态文件膨胀、真相混杂 | 过程进日志，状态留任务板 |
| 覆盖或删除旧日志 | 中断恢复断链、证据丢失 | 追加 `## 续跑记录` |
| 任务无「交付/验收」 | 无法判定完成 | 写可执行、可判定的验收 |
| 一个任务改 30 个文件 | 无法独立验证、难回滚 | 拆分为 ≤10 文件的子任务 |
| 冲突只在对话里说 | 下次会话即丢失 | 记入「待裁决与遗留项」 |
| 验收写「应该通过」 | 无证据、不可审计 | 贴真实命令与结果 |
| 每任务强制 commit | 噪音、违反仓库约束 | 仅用户要求时提交 |
| 新建迭代复用旧目录 | 编号与状态污染 | 新迭代新建目录 |
